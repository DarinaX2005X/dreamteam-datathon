# 03 Сервис: очередь, хранение, API жюри и интерфейса, публичный запуск
Status: active

Цель этапа: сервис принимает записи от жюри и от проверяющего, надёжно обрабатывает их по очереди в пределах 5 минут, переживает перезапуск, хранит результаты и решения, отдаёт API по контрактам и запускается одним образом без интернета. 03.1 стартует сразу после 01.3 и до готовности движка работает с `FakePipeline` по фикстурам. 03.2 готовит образ и публичный адрес.

Завершение: S03, S08, S09 выполнены на реальном конвейере (после 05.1), публичный адрес отвечает на `GET /api/ui/health`.

## 03.1 Задания, хранилище, API v1 и API интерфейса
Status: active
Requirements: R01, R07, R10, R15, R18, R26, R29
Depends on: 01.3
Owner: SUBAGENT contracts_service
Paths: backend/navidu/service/, backend/tests/service/

**Запуск и параллелизм:** нужны контракты 01.3 (модели C-API-V1, C-UI-API, C-ERR, C-DATA, `Pipeline` Protocol). Параллельно с 02.x, 04.x. Реальный конвейер подключается в 05.1. До этого `service/fake_pipeline.py` воспроизводит события и артефакты из `contracts/fixtures/` с реальными задержками фаз из 01.4 (помечен как тестовый и недоступен в production-конфигурации).

**Результат:** жюри получает ответ строго по схеме кейса, проверяющий загружает запись, видит ход анализа, принимает решения и пересчитывает правила; ни одно задание не теряется и не дублируется при перезапуске.

**Входы и выходы:**
- `service/app.py`: FastAPI-приложение: роуты `/api/v1/*`, `/api/ui/*`, раздача собранного фронтенда из `web/dist` (`/`, `/app`, `/app/*` → `index.html`), `/assets/*` с кэшированием. Точка входа `python -m navidu.service` (веб) и `python -m navidu.service.worker` (обработчик).
- `service/store.py` + `service/migrations/0001_init.sql`: таблицы C-STORE, WAL, транзакции на смену статуса.
- `service/queue.py`: аренда заданий, продление, возврат просроченных, лимит попыток, приоритет `api` над `ui`, лимит активных UI-заданий на IP (хеш IP с солью, сам IP не хранится).
- `service/uploads.py`: потоковая запись multipart на диск с лимитом размера (без чтения в память), sha256 на лету, ffprobe-проверка, отказ по C-ERR.
- `service/api_v1.py`: POST/GET по C-API-V1; сериализация только ключей схемы; `verdict` по ревизии 1.
- `service/api_ui.py`: все маршруты C-UI-API, включая `Range` для видео, кадры с оверлеем и без, решения с `base_revision`, `reevaluate` (вызывает `Pipeline.reevaluate`, сохраняет новую ревизию, если не `dry_run`), `rules` (из `rules/catalog` и `rules/sources`), `example`, `health`.
- `service/retention.py`: периодическое удаление видео и результатов по срокам C-STORE (кроме примера), журнал удалений.
- `service/auth.py`: ключи из `NAVIDU_API_KEYS`, `hmac.compare_digest`, без ключа сервис не стартует в production-режиме (явная ошибка конфигурации).
- Логи: JSON-строки с `request_id`, `check_id`, фазой, длительностью; без содержимого кадров и без ключей.

**Поведение и состояния:**
- Загрузка 29 МБ занимает секунды; ответ POST приходит после записи и ffprobe (не после анализа).
- Очередь переполнена (`NAVIDU_QUEUE_MAX`, по умолчанию 20): 429 с `Retry-After`.
- Перезапуск сервиса: задания с истёкшей арендой возвращаются в очередь; GET на них отвечает `processing`.
- Решение по эпизоду с устаревшей `base_revision` → 409, тело содержит текущую ревизию, чтобы клиент мог показать конфликт без потери заметки.
- Пример: `is_example=true`, `PUT decision` → 409 `READ_ONLY_EXAMPLE`, `reevaluate` только с `dry_run`.
- `GET /api/v1/jobs/{id}` для задания, созданного через UI, тоже работает (единая сущность), а для `job_id` не из этой базы → 404.

## 03.2 Образ, офлайн-запуск и публичный адрес
Status: active
Requirements: R08, R10, R16
Depends on: 01.3
Owner: SUBAGENT deploy
Paths: deploy/, Dockerfile, docker-compose.yml, .dockerignore, .env.example, scripts/smoke_api.py

**Запуск и параллелизм:** нужны работающий сервис 03.1 (пусть с `FakePipeline`) и выбор устройства и моделей из 01.4. Параллельно с 02.x и 04.x. Реальные веса подключаются, когда их даст 02.1; до этого образ собирается с базовыми весами из манифеста.

**Результат:** сервис поднимается одной командой на машине с GPU или без, работает без интернета после сборки, доступен по публичному HTTPS-адресу, а жюри и команда могут прогнать API скриптом.

**Входы и выходы:**
- `Dockerfile`: многоступенчатая сборка: (1) Node собирает `web/dist` (и `landing` через workspace), (2) Python-образ с ONNX Runtime GPU (база `nvidia/cuda:*-runtime` или `python:3.11-slim` для CPU через `--build-arg DEVICE=cpu`), ffmpeg, `fetch_models.py` скачивает веса на этапе сборки, (3) финальный образ без компиляторов. Пользователь непривилегированный.
- `docker-compose.yml`: сервисы `web` и `worker` на одном образе, том `data/`, переменные из `.env`, healthcheck на `/api/ui/health`, `deploy.resources` для GPU.
- `deploy/README.md`: два варианта публичного адреса: (а) VPS с GPU и Caddy (`deploy/Caddyfile`, автоматический TLS); (б) машина команды и туннель (`cloudflared` или аналог; конфигурация без секретов, токен в `.env`). Выбор зависит от ответа на вопрос A1.
- `deploy/offline-check.sh`: запуск контейнера с `--network none` и обработка записи из примонтированного файла → ожидание `done` (S09).
- `scripts/smoke_api.py`: `--base`, `--key`, `--files a.mov b.mov`, `--parallel N`; печатает статус, время до `done`, число эпизодов и валидирует ответ по схеме (используется в 05.2 и при передаче жюри).
- `.env.example`: все переменные C-CONFIG с безопасными значениями и комментариями.

**Поведение:** ошибка конфигурации (нет ключей, нет весов) видна сразу при старте, контейнер не уходит в цикл перезапусков молча. Логи читаются через `docker compose logs`.
