# 02 Движок анализа: от кадров к эпизодам с кадром, описанием и нормой
Status: active

Цель этапа: настоящий локальный конвейер `analyze()` превращает запись кассы в FindingSet по C-DATA, а `reevaluate()` пересчитывает правила по правкам проверяющего без повторного восприятия. 02.1 (восприятие), 02.2 (сцена и факты) и 02.3 (правила и доказательства) идут параллельно по контрактам 01.3. 02.4 собирает их в конвейер и калибрует на разметке.

Общие правила: всё работает локально (локальный runtime выбранной модели ONNX Runtime или PyTorch, CUDA/CPU по фактической проверке). Никакой распознавания лиц: модели поз используются для тела и кистей, лицевые точки отбрасываются сразу после инференса и не сохраняются. Тестовые видео жюри не попадают ни в какие наборы. Каждый модуль имеет чистый вход и выход по C-DATA, поэтому тесты пишутся на сохранённых артефактах реальных роликов (`backend/tests/data/` содержит JSON-артефакты без видео; ролики берутся из `NAVIDU_DATASET_DIR`, а тесты, которым нужен ролик, помечаются `@pytest.mark.dataset` и пропускаются без него).

Параллельно с 02.2 (работает на сохранённых артефактах восприятия из 01.4) и 02.3.

**Результат:** из любой записи .mov получаются треки людей с позами кистей и треки объектов (деньги, сумки, телефоны, открытое хранилище) с временем в секундах по C-UNITS и с событиями прогресса. Это сырьё для фактов.

**Входы и выходы:**
- Вход: путь к видео, `PipelineConfig` (`analysis_fps`, `device`, пороги детекции).
- `ingest/probe.py`: ffprobe → `VideoMeta` (поворот, длительность, `start_time`), отказ `UNSUPPORTED_MEDIA` или `VIDEO_TOO_LONG`.
- `ingest/frames.py`: генератор `(t_sec, frame_rgb)` с прореживанием по времени, а не по номеру кадра (VFR); отдельная функция `frame_at(t_sec)` для полного разрешения в 02.3.
- `perception/people.py`: детектор людей + трекер → `Track(kind=person)` с `samples` (bbox, score) и ключевыми точками тела и кистей (17 тела + 2×21 кисти или эквивалент) в `perception/keypoints.jsonl`.
- `perception/objects.py`: дообученный детектор объектов (классы из 01.1) + трекер → `Track(kind=object)`.
- `training/detector/`: скрипт дообучения на `research/dataset/annotations/` (разбиение по роликам), экспорт в ONNX, метрики mAP по классам на отложенных роликах, запись весов в `models/` и хешей в `models/manifest.json`.
- `scripts/fetch_models.py`: скачивание базовых весов по манифесту с проверкой sha256; наши дообученные веса берутся из релиза команды или собираются локально командой `make models`.
- События: `emit(PipelineEvent(phase="perception", processed_until_sec=t))` не реже раз в 5 с видео.

**Поведение:** повороты из метаданных применяются до инференса; кадры с пустой детекцией остаются валидными; при `should_stop()` выход без частичной записи. Трекер переживает кратковременные перекрытия (заданный буфер потери) и не меняет ID человека за стойкой при проходе клиента мимо.

## 02.2 Схема сцены, роли и лента наблюдаемых фактов
Status: active
Requirements: R11, R26, R27
Depends on: 01.3
Owner: SUBAGENT to assign
Paths: backend/navidu/scene/, backend/navidu/facts/, backend/tests/facts/

**Запуск и параллелизм:** нужны описание сцены и типов из 01.1, контракты `Zone`, `Observation`, `Coverage` из 01.3, сохранённые выходы восприятия 01.4 (`research/spike/artifacts/*.jsonl`) как реальные входы для разработки. Финальная проверка идёт на выходах 02.1 в 02.4. Параллельно с 02.1 и 02.3.

**Результат:** из треков получаются понятные человеку факты во времени («кассир на посту», «клиент у окна», «деньги в руках кассира», «стол не виден»). Схема сцены строится автоматически на новом ракурсе, без ручной калибровки, и её можно поправить.

**Входы и выходы:**
- `scene/layout.py`: `infer_layout(tracks, object_tracks, frames_sample) -> SceneLayout`. Сторона кассира и клиента определяются по устойчивым позициям людей (кто дольше всего неподвижен у стола, кто сменяется), положению стойки и лотка (детектор объектов), распределению движений. Зоны `cashier_post`, `client_window`, `cash_desk`, `storage`, `service_door` строятся как полигоны в нормированных координатах. Допускается `count_room`, если 01.1 найдёт такую сцену.
- `scene/roles.py`: `assign_roles(tracks, layout) -> {track_id: Role}` по времени в зонах и поведению (инкассатор: входит через служебную дверь или к лотку с сумкой, коротко; кассир: дольше всех на посту; клиент: у окна со стороны клиента). Роль не зависит от внешности.
- `facts/observations.py`: `derive(tracks, keypoints, layout, roles) -> list[Observation]`: `person_in_zone` (с ролью), `cash_in_hands` (пачка у кисти кассира в пределах порога), `cash_on_desk` (деньги в зоне стола без кисти рядом), `cash_handover` (деньги переходят между людьми или в лоток), `counting_motion` (повторяющееся движение кистей над деньгами), `phone_visible`, `bag_present`, `bag_opened`, `storage_open`.
- `facts/coverage.py`: `derive_coverage(...) -> list[Coverage]`: интервалы, где кассир вне кадра, стол перекрыт (детекция стола и доля перекрытия), низкая освещённость, смаз.
- Сглаживание: факты короче минимальной длительности объединяются или отбрасываются; параметры в `facts/params.yaml` (калибрует 02.4).

**Поведение:** при неуверенной схеме сцены (`camera_note` и `layout.confidence` низкая) это видно в CheckDetail, правила не придумывают зоны. Замена роли или зоны проверяющим меняет только аргументы `derive`, и факты пересчитываются детерминированно (для `reevaluate` в 02.4 достаточно пересчёта фактов, зависящих от ролей и зон, без восприятия).

## 02.3 Правила из норм, таймкод, описание и кадры-доказательства

Depends on: 01.2, 01.3

Paths: backend/navidu/rules/, backend/navidu/evidence/, rules/catalog/, backend/tests/rules/, backend/tests/evidence/

**Запуск и параллелизм:** нужны сверенные источники 01.2 и схемы C-RULES/C-SRC/C-DATA из 01.3. Вход (наблюдения) берётся из фикстур и ручных JSON, поэтому задача идёт параллельно с 02.1 и 02.2. Финальная проверка на реальных фактах проходит в 02.4.

**Результат:** любая лента фактов детерминированно превращается в эпизоды с типом, окном, таймкодом, кадрами, описанием из фактов и ссылкой на норму, а также в статусы всех правил, включая «нельзя проверить».

**Входы и выходы:**
- `rules/catalog/*.yaml`: правило на каждый тип из PROJECT, подтверждённый в 01.1/01.2 (начальный набор: V-COUNT-ABSENT, V-LEFT-POST, V-CASH-UNSECURED, V-PERSONAL-ITEMS, V-OUTSIDER, V-BAG-OPENED-ALONE, V-COUNT-NO-CONTROLLER; выключенные помечаются `enabled: false` с причиной).
- `rules/engine.py`: интерпретатор условий C-RULES над `Observation`/`Coverage`, `evaluate(observations, coverage, layout, roles, catalog, thresholds) -> (findings_without_frames, rule_statuses)`.
- `rules/timecode.py`: политики `max_evidence` (момент максимального совпадения условий, например середина пересечения «деньги в руках» и «нет клиента» с наибольшей уверенностью), `onset` (начало), `obligation_due` (для бездействия: момент, когда обязанность должна была выполниться). Смещение по типу калибрует 02.4 (`rules/calibration/timecode_offsets.yaml`, по умолчанию 0).
- `rules/describe.py`: заполнение шаблонов `what_seen` и `why_may_violate` значениями из фактов (длительности, время «с 00:38,4»), сборка `description` по C-DATA. Свободного текста нет.
- `evidence/frames.py`: выбор 1–3 кадров (основной в `timecode_sec`, плюс начало и конец окна, если они дают новую информацию), извлечение полного разрешения через `frame_at`, JPEG (≤ 1280 px, q85), оверлей (рамки участников эпизода: голубые для наблюдений, коралловые углы для объекта эпизода; подписи на русском; шрифт Open Sans из `backend/navidu/evidence/fonts/`, а если шрифта нет, используется встроенный, без сети).
- Политика неопределённости: если на окне правила есть `Coverage` по требуемой области (`requires_visible`), эпизод не создаётся, а правило получает `not_checkable` с окном. Слабые совпадения (`strength: moderate`) создают эпизод только при выполнении порога 02.4.

**Поведение:** эпизоды одного правила, перекрывающиеся или ближе 3 с, сливаются. Один и тот же момент может породить эпизоды разных правил, если условия независимы. Порядок вывода по `timecode_sec`.
