# Передача проектной основы «Навиду»

Это переносимая основа для следующего исполнителя: продуктовое решение, айдентика, контракты и план в штатной структуре VibeMachina. Работающего продукта, процессов, назначений и git-истории в архиве нет.

## Выбранный вариант

**Навиду** («Смотрите главное, а не всю запись») — локальный сервис для проверяющего. Он находит на записи кассы видимые признаки нарушений кассовой дисциплины и для каждого показывает тип, таймкод, 1–3 кадра с разметкой, описание из наблюдений и пункт нормативного акта РК. Механизм: восприятие (люди, кисти, деньги, сумки, телефоны) → автоматическая схема сцены и роли → лента наблюдаемых фактов → правила, выведенные из пунктов норм → эпизоды. Слой фактов даёт проверяемые описания, честный статус «нельзя проверить» и мгновенный пересчёт после правки роли проверяющим. Подробно: `.vibemachina/PROJECT.md`, раздел «Концепция и её проверка».

## Что проверено, а что гипотеза

Проверено 2026-10-17:
- брендбук forte.kz/en/logo (4 цвета, градиенты, Open Sans 300–800);
- Open Sans содержит кириллицу и казахские буквы, `tnum`; npm `@fontsource-variable/open-sans` 5.3.0 (OFL);
- номера пунктов норм: пост. Правления НБРК № 231 от 29.11.2019 (п. 12, 20, 22, 24–25, 31, 35, 38–39, 42, 74–78, 99) и № 14 от 24.02.2020 (п. 8, 12, 16, 20, 21) по копии на zakon.uchet.kz;
- контраст токенов (`identity/tokens/contrast.md`);
- `check-plan.mjs` → `ok: true` (7 этапов, 22 задачи, 40 подшагов, 30 требований, без конфликтов путей);
- дашборд извлекает название, слоган, логотип, цвета и шрифт без предупреждений.

Гипотезы, которые проверяются первыми задачами:
- формат разметки и реальные типы нарушений в датасете (датасет не передавался) → задача 01.1;
- дословные цитаты норм и актуальность нумерации → 01.2; до сверки цитаты в продукте не показываются;
- модели, частота анализа и укладывание в 5 минут → 01.4;
- допущения A1–A6 в PROJECT («Решения, допущения и границы»): железо, собственные съёмки, дата дедлайна, формат разметки, ссылка на презентацию, разметка на кадрах API.

## Статус утверждения

Пользователь план **не утверждал**. STATE: `Phase: awaiting-approval`, `Approval: pending`. Пользователю заданы три вопроса (железо, собственные съёмки, дата дедлайна), ответов нет. Реализацию начинать только после явного утверждения пакета; ответ и версию пакета записать в STATE и BRIEF.

## Как запустить штатный дашборд

Скилл VibeMachina в архив не входит. Его устанавливают отдельно; ниже `<skill>` означает путь к установленному скиллу, `<project>` — корень распакованного архива.

```bash
node <skill>/scripts/init.mjs <project> --timezone Asia/Yekaterinburg   # создаёт только недостающее (runtime/), ничего не перезаписывает, печатает URL
node <skill>/scripts/dashboard.mjs <project> --detach                   # повторный запуск в фоне; --port N для другого порта
node <skill>/scripts/dashboard.mjs <project> --stop                     # остановка своего экземпляра
node <skill>/scripts/check-plan.mjs <project>                           # проверка плана: структура, покрытие, пути, готовые задачи
```

Часовой пояс задан по пользователю (UTC+5; для Казахстана подходит и `Asia/Almaty`). Каталог `.vibemachina/runtime/` исключён из архива и создаётся заново. Адрес дашборда в STATE не записывается: он локальный у каждого исполнителя.

## Исходники айдентики

- Логотип: `identity/logo/navidu-logo.svg` (связка), `navidu-mark.svg` (знак), моно-, тёмные варианты и `favicon.svg`.
- Значения: `identity/tokens/tokens.json` (единственный источник) → `tokens.css` (сгенерирован).
- Визуальные опоры: `identity/compositions/hero-desktop.svg`, `hero-mobile.svg`, `workspace-desktop.svg`, `workspace-mobile.svg` и иллюстрации `identity/art/*.svg`; превью в `identity/previews/`.
- Пересборка: `python3 identity/source/build_art.py`, затем `OPEN_SANS_TTF=… python3 identity/source/build_identity.py` (шрифт берётся из google/fonts, в архив не входит).

## Контракт для исполнителя лендинга

Полностью: PLAN.md, раздел **C-LANDING**; задача: `stages/04-interface.md`, **04.5**. Коротко:
- пакет `landing/` (`@navidu/landing`, React 18 + TypeScript), экспорт `Landing(props: LandingProps)` из `landing/src/index.ts`;
- `LandingProps = { dashboardHref: string; presentationHref?: string | null; onNavigate?; rules: LandingRule[] }`. Ссылка на презентацию выводится только при непустом `presentationHref` (`VITE_PRESENTATION_URL`); кнопки видео нет;
- стили только под `[data-surface="landing"]`/`.nv-landing`, значения только из `--nv-*` (`identity/tokens/tokens.css`), без глобальных стилей и `@font-face`;
- автономная разработка в `landing/dev/` с примерными правилами; подключение на `/` делает MAIN в 05.1;
- исполнитель лендинга не владеет `/app`, backend, `identity/` и `.vibemachina/`.

## С чего начинает GPT

1. Прочитать `<skill>/SKILL.md` и `<skill>/references/flow/memory.md`, затем `.vibemachina/STATE.md`; не начинать discovery заново и не переписывать план.
2. Запустить дашборд (команды выше) и дать пользователю ссылку.
3. Показать пользователю пакет (название, слоган, логотип, композиции, PLAN-HUMAN) и получить **явное** утверждение или правки, а также ответы на вопросы A1–A3. Записать ответ дословно в BRIEF, утверждение и версию пакета в STATE (`Approval: approved`, `Phase: build`). Тишина не считается согласием.
4. После утверждения: создать git-репозиторий, сделать commit пакета планирования, запустить первую волну задач **01.1, 01.2, 01.3, 01.4** и **04.5** (готовы по `check-plan.mjs`), записав владельцев в STATE до запуска.
5. По мере приёмки 01.3 и 04.1 настроить `vibemachina.checkpoint.json` на реальные проверки; не добавлять фиктивных проверок.
