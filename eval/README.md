# Воспроизводимая оценка конвейера

Все видео, кадры, промежуточные описания модели и результаты отдельных записей остаются в рабочем окружении проекта: на локальной машине либо на явно разрешённом пользователем частном GPU-сервере. Оценщик не обращается к внешним AI API. Он вызывает тот же `navidu.pipeline.run.RealPipeline`, который использует сервис, и читает фактические `AnalysisArtifacts`. По текущему решению пользователя все новые тяжёлые inference-запуски и обучение выполняются только на удалённом L40S; локально допустимы статические проверки, unit-тесты и подготовка данных.

## Данные и фиксированное разбиение

`labels.csv` — буквальное преобразование разметки организаторов. В `X-1`, `X-2` латинская X; начиная с `Х-3` — кириллическая Х. Типы событий организаторами не указаны; `type_code` пустой. Точность классификации поэтому недоступна.

`source-labels.json` объединяет одинаковые байты по SHA256. Х-4 и Х-47 — один файл, но метки 57 и 68 с различаются: сохраняем обе как спорные исходные аннотации, **не считаем двумя подтверждёнными событиями**, исключаем источник из основной метрики таймкода. На вердикт это не влияет: обе исходные строки положительные. Копии Х-5/Х-48 отрицательные.

`folds.csv` содержит 5 фиксированных фолдов по 8 уникальных источников. Всего 40 источников и 42 исходные строки. Фолды 1–4 (32 источника: 16 положительных, 16 отрицательных) — разработка и настройка; **fold 0 (8 источников: 5 положительных, 3 отрицательных) зарезервирован** до заморозки параметров. Все кадры и копии одного SHA должны оставаться в одном фолде. Фолды одной сцены не заменяют независимую запись нового ракурса.

## Разметка для обучения

`training-splits.json` фиксирует внутреннее разбиение development: фолды 1–3 — **24 уникальных источника для обучения** (12 положительных, 12 отрицательных), фолд 4 — **8 для выбора параметров** (4 положительных, 4 отрицательных). Фолд 0 отсутствует в списке обучающих примеров; в манифесте доступны только его агрегированные числа. Создать этот манифест из неизменённых таблиц можно командой `python eval/training.py`.

Обучающий код должен пользоваться `eval.training.load_training_partition`, передавая пути к манифесту, inventory, labels, folds, папке dataset и `partition="train"` либо `"validation"`. Reader сверяет весь манифест с исходными таблицами, проверяет группировку и SHA256 выбранных файлов до возврата данных. `partition="holdout"` запрещён. В `TrainingSample` доступны `video_path`, `duration_sec`, `has_violation`, `time_sec`, `time_supervision`; идентификатор/SHA предназначены только для группировки и воспроизводимости.

Цели содержат только бинарную метку и подтверждённый организатором таймкод. Отрицательные записи не имеют временной цели. При спорных таймкодах одинакового файла бинарная метка сохраняется, а временная потеря маскируется. Из бинарной метки нельзя создавать псевдоразметку роли, действия или конкретного пункта правил.

Положительное окно, содержащее известную временную метку, можно выбирать для обучения. Остальные окна положительного видео нельзя автоматически превращать в отрицательные. Для validation, итоговой оценки и продуктового inference выбор кадров и окон обязан быть независимым от меток и исходных таймкодов. Имя файла, путь, SHA, фолд и координаты кропа, полученные из целевой метки, не входят в модельный prompt.

После выбора параметров на внутренних train/validation допускается отдельное окончательное переобучение на `partition="development"` (32 источника). Такой запуск требует отдельной фиксации гиперпараметров и весов перед единственным итоговым holdout. Метрики train/development, внутренних validation и финального holdout хранятся отдельно.

## Ограниченный перенос на разрешённый сервер

`prepare_transfer.py` собирает один исходный MOV на уникальный SHA, три таблицы оценки и манифест обучения. Получается 40 видео и 4 файла метаданных, плюс внутренний список контрольных сумм. Архив не содержит кадров, ответов модели, весов, кэша и пользовательских загрузок. Передача байтов восьми зарезервированных видео не разрешает использовать их для обучения или подбора параметров.

```text
python eval/prepare_transfer.py prepare
python eval/prepare_transfer.py verify --archive eval/runs/transfer/dataset-40sha-e35f46baf71b.tar
```

Уже подготовленный архив имеет размер **263833600 байт**, SHA256 `204125200f943943508dd0bb67bfb724873897a4d865a11e3f030e20ac383a6e`. Повторная команда `prepare` не перезаписывает существующий архив. Его `.sha256` и `.manifest.json` находятся рядом в игнорируемой папке `eval/runs/transfer/`.

После копирования в согласованное постоянное хранилище сервера сначала сравните SHA256 всего архива, затем выполните проверку и извлечение из корня проекта:

```bash
sha256sum eval/runs/transfer/dataset-40sha-e35f46baf71b.tar
python eval/prepare_transfer.py verify --archive eval/runs/transfer/dataset-40sha-e35f46baf71b.tar
python eval/prepare_transfer.py extract --archive eval/runs/transfer/dataset-40sha-e35f46baf71b.tar --destination .
```

Извлечение сначала проверяет все назначения. Одинаковые существующие файлы переиспользуются; отличающиеся не перезаписываются. Внутренние манифесты сохраняются отдельно по SHA архива в `eval/runs/transfer/manifests/`, поэтому небольшой пакет можно безопасно дополнить полным. Таблицы должны сохранять точные байты, включая переносы строк: fingerprint связывает оценку с их SHA256. При различии существующей таблицы сначала выясните причину, не заменяйте её автоматически.

Для первоочередного запуска шести заранее выбранных источников подготовлен `dataset-6sha-e35f46baf71b-e41ee3941ea5.tar`: **25098240 байт**, SHA256 `ba5862dcf34d668d963a20488a582989d46a708bb1daa593b9230fac23ddb8bc`. Он содержит только эти шесть оригиналов и те же четыре полные таблицы; holdout-видео отсутствуют. Его достаточно для выбранного baseline, но недостаточно для обучения на 24 источниках и validation на восьми. Повторяемая команда подготовки: `python eval/prepare_transfer.py prepare --video-id X-1 --video-id X-2 --video-id Х-3 --video-id Х-17 --video-id Х-21 --video-id Х-40`. Для извлечения используйте актуальный helper с раздельным сохранением манифестов; затем полный архив переиспользует общие байты и добавляет остальные файлы.

## Подготовка таблиц и тесты

Из корня репозитория:

```text
python eval/convert_labels.py data/dataset/open/open_labels.xlsx --videos-dir data/dataset/open/videos
python research/dataset/inventory.py --dataset-dir data/dataset
python eval/make_splits.py
python -m unittest discover -s eval -p "test_*.py" -v
```

Тесты используют явно синтетические числовые примеры исключительно для проверки формул, не как измеренное качество модели. Проверяются реальные таблицы, группировка копий, недоступность тайминга при спорных метках, знаменатели при ошибках, отсутствие приватных описаний в отчёте, безопасное восстановление и защита holdout.

## Настоящий запуск

Нужны установленные зависимости backend/runtime и локально размещённые веса, прошедшие проверку SHA256. На Linux используйте Python из настроенного окружения проекта. Проверка наличия моделей не выполняет inference:

```text
python eval/run_pipeline.py preflight
```

Первые реальные проверки только на development. Следующий согласованный baseline на удалённом L40S — InternVL3.5-4B bf16 с квантованным RF-DETR на CPU. Параметры задаются в одной shell-сессии:

```bash
export NAVIDU_DETECTOR_MODEL=rfdetr-nano-onnx
export NAVIDU_SEMANTIC_MODEL=internvl3_5-4b
export NAVIDU_SEMANTIC_DTYPE=bf16
export NAVIDU_SEMANTIC_MAX_PATCHES=1
export NAVIDU_SEMANTIC_MAX_NEW_TOKENS=384
export NAVIDU_SEMANTIC_WINDOW_FRAMES=8
export NAVIDU_SEMANTIC_FPS=1
export NAVIDU_DETECTION_THRESHOLD=0.45
export NAVIDU_CPU_THREADS=6
python eval/run_pipeline.py run --split development --video-id Х-40 --video-id Х-21 \
  --device auto --analysis-fps 3 --runtime-label brev-l40s-4b-cpu-detector \
  --output-root eval/runs/brev-l40s-4b-cpu-detector \
  --aggregate-report eval/reports/brev-l40s-4b-development-pair
```

Это команда будущего измерения, а не утверждение о его результате. Следующий этап — тот же неизменённый профиль на заранее выбранных шести источниках, перечисленных ниже; передайте все шесть `--video-id`, сохранив каталог и параметры. Полная оценка 32 development-источников остаётся отдельным этапом. Запуск адаптера после обучения должен иметь собственный профиль и каталог результатов.

Перед измерением следующего профиля зафиксирован `reports/brev-l40s-4b-publication-plan.json`: точный checkpoint, веса/таблицы, шесть источников X-1, X-2, Х-3, Х-17, Х-21, Х-40 и пороги. Пара служит только smoke-проверкой; её оба результата сохраняются при расширении до шести. Для временного допуска профиля к пользовательской проверке нужны все шесть завершений без ошибок, precision ≥ 0.8, recall ≥ 0.75, ни одного ложного срабатывания, оба чистых источника с проверяемыми правилами, p90 ошибки таймкода ≤ 5 с и полный анализ каждого ролика ≤ 300 с на L40S. Холодная загрузка измеряется отдельно.

Это заранее объявленный небольшой тест профиля. Он не заменяет итоговый holdout и не устанавливает точность каждого правила. План содержит `planned_not_measured`, не является результатом измерения и сам не включает readiness. Состав выборки и пороги нельзя ослаблять после получения результатов.

Профиль наследует параметры конвейера из `NAVIDU_*`; явные параметры — `--device cpu|cuda|auto` и `--analysis-fps`. CPU для детектора и CUDA для временной модели могут дать реальное устройство `cpu+cuda`. Нельзя называть это полноценным CUDA-профилем детектора. Достоверная версия берётся после загрузки через публичный `runtime_status().pipeline_version`; она учитывает выбранные веса, код, правила, параметры, пакеты и фактические устройства.

Оценщик явно устанавливает `PipelineConfig(diagnostic_only=True)`. Это позволяет измерять ещё не валидированные возможности локальной реализации: события модели проходят факты и правила, а `AnalysisRun` обязательно остаётся `analysis_ready=False`, `analysis_mode="diagnostic"`. Список проверяемых возможностей и этот режим сохраняются в профиле; режим входит в fingerprint. Сервис не должен публиковать такие артефакты как готовую пользовательскую проверку. Бинарные метки организаторов не подтверждают точность отдельных признаков; оценщик не создаёт `models/validation.json` и не включает продуктовый статус готовности.

Отдельный `algorithm_fingerprint` берётся из публичного `runtime.quality_binding` после загрузки. Он связывает измерение с точными весами, кодом, параметрами, возможностями реализации и фактическими устройствами, исключая файл валидации и цель публикации. Эффективный `fingerprint` кэша сохраняет эти поля. Такое разделение позволяет отдельно принять измеренный алгоритм без самоссылки на хеш его будущего свидетельства проверки; оценщик не принимает решение о готовности автоматически.

Веса загружаются один раз на процесс. Каждый ролик получает отдельные треки и артефакты. При изменении исходников или эффективной версии во время работы запуск прерывается; продолжить можно новым процессом с новым профилем. Одновременно допускается один запуск оценщика через блокировку ОС. При внешних исследованиях модели согласуйте GPU с их исполнителем: блокировка не управляет сторонними процессами.

По умолчанию выход — игнорируемая `eval/runs/`: `profiles/<fingerprint>/sources/<sha>/attempt-*/`, неизменяемые результаты попыток, атомарный `complete.json` только после успешного завершения, приватные журналы и кадры. Кэш переиспользуется только при совпадении источника и эффективной версии и после проверки хешей завершённых артефактов. Частичная попытка никогда не считается кэшем. Для повтора неудачных источников добавьте `--retry-failed`; удачные источники не пересчитываются.

Профиль и отчёт отдельно сохраняют ОС, архитектуру, CPU/RAM, Python и реально используемый CUDA GPU, а также `hardware_fingerprint` и необязательный `--runtime-label`. В аппаратные данные не входят hostname, имя пользователя или пути. При смене характеристик машины или метки запуск требует отдельный `--output-root`: скорость ноутбука нельзя переиспользовать как скорость L40S. Исторические отчёты без аппаратного снимка остаются читаемыми, но их кэш не принимается для нового запуска. Замороженная итоговая сессия также требует неизменённую аппаратную привязку.

Локальный детектор без временной модели можно проверить отдельно:

```text
python eval/run_pipeline.py run --split development --video-id X-1 --detector-only --device cpu
```

Это **диагностика объектов**, для неё намеренно не рассчитываются метрики обнаружения нарушений и таймкода. Она не доказывает решение кейса и не допускается как финальный профиль.

## Итоговый holdout

После завершения настройки и принятия development-результатов зафиксируйте те же параметры и заморозьте профиль:

```text
python eval/run_pipeline.py freeze --device auto --analysis-fps 3 --runtime-label <final-runtime-label> --output-root <final-output-root>
python eval/run_pipeline.py run --split holdout --device auto --analysis-fps 3 --runtime-label <final-runtime-label> --output-root <final-output-root>
```

Заморозка и запуск должны иметь те же параметры/устройства/веса. Сохранённые `eval/runs/frozen-profile.json` и `holdout-session.json` запрещают заменить профиль и повторно подобрать его под fold 0. После сбоя разрешено только точное продолжение исходного профиля с сохранением успешных результатов. Выбирать отдельные видео holdout вместо полного фолда CLI не позволяет. Не удаляйте эти файлы ради улучшения показателя.

## Метрики и отчёт

Основные TP/FP/TN/FN, accuracy, precision, recall, F1, balanced accuracy и false-positive rate на чистых видео вычисляются по **уникальным SHA**, только по завершённым результатам. Рядом обязательно показаны число выбранных/завершённых/ошибочных/отсутствующих источников, доля завершения, нижняя граница accuracy по всем выбранным и recall с ошибками/пропусками как недетектированными положительными. Ошибка не превращается в `no_violation`.

Диагностический `no_violation` с непроверяемыми правилами остаётся виден в исходной матрице, но не становится свидетельством успешной проверки чистого видео. Отдельные счётчики показывают истинно отрицательные результаты хотя бы с одним проверяемым правилом (`no_violation` или `partly_checkable`) и более строгий вариант хотя бы с одним полностью проверяемым правилом (`no_violation`). Пустой список правил не подходит ни под один вариант. Это не утверждает, что проверялись все правила и все интервалы; принятие E2E-профиля должно учитывать эти счётчики и охват.

Таймкод: медиана/p90/max абсолютной разницы между единственной однозначной меткой и ближайшим фактическим finding, только среди правильно обнаруженных положительных источников. Это не взаимно однозначное сопоставление событий и может благоприятствовать роликам с большим числом findings. Спорная группа Х-4/Х-47 исключена. Число пропущенных/необработанных положительных показывается отдельно, а диагностика исходных строк с копиями хранится отдельно от основных метрик.

Задержка: median/p90/max полного `analyze` при уже загруженной модели, включая декодирование, inference, правила и доказательства. Подготовка модели измеряется отдельно. При повторном чтении кэша используется исходное измерение реального анализа; время чтения кэша не выдаётся за новую скорость inference. Интерполяция p90: `(n−1)×0.9`, линейная.

Агрегаты записываются автоматически; разрешён отдельный путь безопасного числового отчёта:

```text
python eval/run_pipeline.py run --split development --aggregate-report eval/reports/development
python eval/run_pipeline.py report --profile <fingerprint> --split development --aggregate-report eval/reports/development
```

После запуска замороженного holdout доступен общий отчёт по 40 источникам с отдельными метриками development и holdout:

```text
python eval/run_pipeline.py report --profile <fingerprint> --split all --aggregate-report eval/reports/combined
```

`--split all` разрешён только для чтения результатов: он не запускает inference, не создаёт сессию holdout и требует совпадения замороженного профиля, таблиц и полного состава fold 0. Ошибки или ещё отсутствующие результаты видны в числах охвата. Объединённые показатели не заменяют независимый итоговый результат holdout.

Команда `report` использует проверенные сохранённые артефакты и не загружает модель. В вывод инструмента и переносимый JSON/Markdown не попадают кадры, имена отдельных роликов, исходные пути и описания модели. Детализация остаётся только в `eval/runs/`.

Не включайте пользовательские загрузки, скрытые видео жюри или данные эксплуатации в обучение/подбор порогов. Имена роликов, SHA и исходные метки не являются входными признаками конвейера. Успешные unit-тесты и детекторная диагностика сами по себе не являются измеренной точностью семантического анализа.
