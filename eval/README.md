# Воспроизводимая оценка локального конвейера

Все видео, кадры, промежуточные описания модели и результаты отдельных записей остаются локально. Оценщик не обращается к внешним AI API. Он вызывает тот же `navidu.pipeline.run.RealPipeline`, который использует сервис, и читает фактические `AnalysisArtifacts`.

## Данные и фиксированное разбиение

`labels.csv` — буквальное преобразование разметки организаторов. В `X-1`, `X-2` латинская X; начиная с `Х-3` — кириллическая Х. Типы событий организаторами не указаны; `type_code` пустой. Точность классификации поэтому недоступна.

`source-labels.json` объединяет одинаковые байты по SHA256. Х-4 и Х-47 — один файл, но метки 57 и 68 с различаются: сохраняем обе как спорные исходные аннотации, **не считаем двумя подтверждёнными событиями**, исключаем источник из основной метрики таймкода. На вердикт это не влияет: обе исходные строки положительные. Копии Х-5/Х-48 отрицательные.

`folds.csv` содержит 5 фиксированных фолдов по 8 уникальных источников. Всего 40 источников и 42 исходные строки. Фолды 1–4 (32 источника: 16 положительных, 16 отрицательных) — разработка и настройка; **fold 0 (8 источников: 5 положительных, 3 отрицательных) зарезервирован** до заморозки параметров. Все кадры и копии одного SHA должны оставаться в одном фолде. Фолды одной сцены не заменяют независимую запись нового ракурса.

## Подготовка таблиц и тесты

Из корня репозитория:

```text
python eval/convert_labels.py data/dataset/open/open_labels.xlsx --videos-dir data/dataset/open/videos
python research/dataset/inventory.py --dataset-dir data/dataset
python eval/make_splits.py
python -m unittest discover -s eval -p "test_*.py" -v
```

Тесты используют явно синтетические числовые примеры исключительно для проверки формул, не как измеренное качество модели. Проверяются реальные таблицы, группировка копий, недоступность тайминга при спорных метках, знаменатели при ошибках, отсутствие приватных описаний в отчёте, безопасное восстановление и защита holdout.

## Настоящий запуск

Нужны установленные зависимости backend/runtime и локальные веса, прошедшие проверку SHA256. На текущем ноутбуке подготовленная среда запускается как `research/spike/.venv310/Scripts/python.exe`; на Linux используйте Python из настроенного окружения проекта. Проверка наличия моделей не выполняет inference:

```text
python eval/run_pipeline.py preflight
```

Первые реальные проверки только на development, например:

```text
python eval/run_pipeline.py run --split development --video-id X-1 --video-id X-2 --video-id Х-3 --video-id Х-17 --video-id Х-21
python eval/run_pipeline.py run --split development
```

Профиль наследует параметры конвейера из `NAVIDU_*`; явные параметры — `--device cpu|cuda|auto` и `--analysis-fps`. CPU для детектора и CUDA для временной модели могут дать реальное устройство `cpu+cuda`. Нельзя называть это полноценным CUDA-профилем детектора. Достоверная версия берётся после загрузки через публичный `runtime_status().pipeline_version`; она учитывает выбранные веса, код, правила, параметры, пакеты и фактические устройства.

Оценщик явно устанавливает `PipelineConfig(diagnostic_only=True)`. Это позволяет измерять ещё не валидированные возможности локальной реализации: события модели проходят факты и правила, а `AnalysisRun` обязательно остаётся `analysis_ready=False`, `analysis_mode="diagnostic"`. Список проверяемых возможностей и этот режим сохраняются в профиле; режим входит в fingerprint. Сервис не должен публиковать такие артефакты как готовую пользовательскую проверку. Бинарные метки организаторов не подтверждают точность отдельных признаков; оценщик не создаёт `models/validation.json` и не включает продуктовый статус готовности.

Отдельный `algorithm_fingerprint` берётся из публичного `runtime.quality_binding` после загрузки. Он связывает измерение с точными весами, кодом, параметрами, возможностями реализации и фактическими устройствами, исключая файл валидации и цель публикации. Эффективный `fingerprint` кэша сохраняет эти поля. Такое разделение позволяет отдельно принять измеренный алгоритм без самоссылки на хеш его будущего свидетельства проверки; оценщик не принимает решение о готовности автоматически.

Веса загружаются один раз на процесс. Каждый ролик получает отдельные треки и артефакты. При изменении исходников или эффективной версии во время работы запуск прерывается; продолжить можно новым процессом с новым профилем. Одновременно допускается один запуск оценщика через блокировку ОС. При внешних исследованиях модели согласуйте GPU с их исполнителем: блокировка не управляет сторонними процессами.

По умолчанию выход — игнорируемая `eval/runs/`: `profiles/<fingerprint>/sources/<sha>/attempt-*/`, неизменяемые результаты попыток, атомарный `complete.json` только после успешного завершения, приватные журналы и кадры. Кэш переиспользуется только при совпадении источника и эффективной версии и после проверки хешей завершённых артефактов. Частичная попытка никогда не считается кэшем. Для повтора неудачных источников добавьте `--retry-failed`; удачные источники не пересчитываются.

Локальный детектор без временной модели можно проверить отдельно:

```text
python eval/run_pipeline.py run --split development --video-id X-1 --detector-only --device cpu
```

Это **диагностика объектов**, для неё намеренно не рассчитываются метрики обнаружения нарушений и таймкода. Она не доказывает решение кейса и не допускается как финальный профиль.

## Итоговый holdout

После завершения настройки и принятия development-результатов зафиксируйте те же параметры и заморозьте профиль:

```text
python eval/run_pipeline.py freeze
python eval/run_pipeline.py run --split holdout
```

Заморозка и запуск должны иметь те же параметры/устройства/веса. Сохранённые `eval/runs/frozen-profile.json` и `holdout-session.json` запрещают заменить профиль и повторно подобрать его под fold 0. После сбоя разрешено только точное продолжение исходного профиля с сохранением успешных результатов. Выбирать отдельные видео holdout вместо полного фолда CLI не позволяет. Не удаляйте эти файлы ради улучшения показателя.

## Метрики и отчёт

Основные TP/FP/TN/FN, accuracy, precision, recall, F1, balanced accuracy и false-positive rate на чистых видео вычисляются по **уникальным SHA**, только по завершённым результатам. Рядом обязательно показаны число выбранных/завершённых/ошибочных/отсутствующих источников, доля завершения, нижняя граница accuracy по всем выбранным и recall с ошибками/пропусками как недетектированными положительными. Ошибка не превращается в `no_violation`.

Диагностический `no_violation` с непроверяемыми правилами остаётся виден в исходной матрице, но не становится свидетельством успешной проверки чистого видео. Отдельные счётчики показывают истинно отрицательные результаты хотя бы с одним проверяемым правилом (`no_violation` или `partly_checkable`) и более строгий вариант хотя бы с одним полностью проверяемым правилом (`no_violation`). Пустой список правил не подходит ни под один вариант. Это не утверждает, что проверялись все правила и все интервалы; принятие E2E-профиля должно учитывать эти счётчики и охват.

Таймкод: медиана/p90/max абсолютной разницы между единственной однозначной меткой и ближайшим фактическим finding, только среди правильно обнаруженных положительных источников. Это не взаимно однозначное сопоставление событий и может благоприятствовать роликам с большим числом findings. Спорная группа Х-4/Х-47 исключена. Число пропущенных/необработанных положительных показывается отдельно, а диагностика исходных строк с копиями хранится отдельно от основных метрик.

Задержка: median/p90/max полного `analyze` при уже загруженной модели, включая декодирование, inference, правила и доказательства. Подготовка модели измеряется отдельно. При повторном чтении кэша используется исходное измерение реального анализа; время чтения кэша не выдаётся за новую скорость inference. Интерполяция p90: `(n−1)×0.9`, линейная.

Агрегаты записываются автоматически; разрешён отдельный путь безопасного числового отчёта:

```text
python eval/run_pipeline.py run --split development --aggregate-report eval/reports/development
python eval/run_pipeline.py report --profile <fingerprint> --split development --aggregate-report eval/reports/development
```

После запуска замороженного holdout доступен общий отчёт по 40 источникам с отдельными метриками development и holdout:

```text
python eval/run_pipeline.py report --profile <fingerprint> --split all --aggregate-report eval/reports/combined
```

`--split all` разрешён только для чтения результатов: он не запускает inference, не создаёт сессию holdout и требует совпадения замороженного профиля, таблиц и полного состава fold 0. Ошибки или ещё отсутствующие результаты видны в числах охвата. Объединённые показатели не заменяют независимый итоговый результат holdout.

Команда `report` использует проверенные сохранённые артефакты и не загружает модель. В вывод инструмента и переносимый JSON/Markdown не попадают кадры, имена отдельных роликов, исходные пути и описания модели. Детализация остаётся только в `eval/runs/`.

Не включайте пользовательские загрузки, скрытые видео жюри или данные эксплуатации в обучение/подбор порогов. Имена роликов, SHA и исходные метки не являются входными признаками конвейера. Успешные unit-тесты и детекторная диагностика сами по себе не являются измеренной точностью семантического анализа.
